# iPhone / iPad 分辨率与自动旋转复审（2026-10-17）

审查覆盖本轮型号目录、无线能力档位、有线 B 自动方向、方向辅助进程、共享 USB mux
以及可运行本地包。以下问题均已在当前源码修复；没有推送或发布版本。

## 发现并修复的问题

### P1：持续音频可能阻止原生 B 回退后恢复视频

原实现仅在 USB 读取空闲或收到显示释放确认时完成 HPD0/HPD1 显示重配。
当方向服务失效、设备未发送 RELS、但音频持续到达时，两项条件都不满足，普通 B 视频
会一直被重配中的状态阻挡。

修复为独立的 `DisplayReconfigureGate`，在每轮传输循环检查释放确认或 1200ms 截止时刻，
与是否收到音频无关；重配期间不会被视频停顿逻辑抢先重连。重新附加显示后更新视频等待基线。
测试模拟每 20ms 一包音频且永不收到 RELS，确认在截止时刻只附加一次普通 B 显示。

### P1：方向查询失败可能连带断开反控共享通道

原生 B 的只读方向进程可能同时是 usbmux broker 的拥有者。原实现一旦 SpringBoard
查询超时、断开或返回未知方向就退出；核心回退时也会停止该进程，使正在借用 broker
的反控连接一起断开。

方向失败现在单独报告不可用并立即撤销缓存方向，释放方向服务，但保留 broker，直到
主进程关闭 stdin 才正常释放 USB 资源。核心回退普通 B 时保留该 broker；最终停止投屏时
仍按原顺序关闭辅助进程并恢复 USB。借用已有 broker 的辅助进程不会覆盖或删除拥有者的端口记录。
测试覆盖查询超时、连接断开、未知方向及父进程断开后的清理。

### P1：借用 broker 的反控恢复分支可能重复占用 USB 接口

正常启动分支已复用 broker，但 Lockdown 恢复分支只检查自己是否拥有本地服务，
没有识别“正在借用其他进程的服务”，设备暂时查不到时仍可能打开第二套 USB transport。

恢复分支现在明确拒绝对借用通道执行 USB 接口接管；新增故障测试确认不会枚举或抢占
拥有者的接口。原有 broker 拥有者恢复成功时也会重新上报新端口，避免继续发布旧地址。

## 第二轮审查：解码排队与逐帧方向（20:42–20:49）

### P2：解码延迟可能丢失收帧时有效的方向

原实现等输入帧解码完成后，才按接收时刻回查系统方向。方向服务只保留有限历史，
当解码器或队列被阻塞较久时，对应历史可能已经淘汰；系统方向仍健康也会误触发
原生 B 回退。方向服务同时失效时，也可能影响此前已经正确接收的帧。

修复为收到视频样本时立即保存当时的方向，随输入帧的 PTS 和接收时刻进入队列，
解码输出只取对应样本保存的值。测试模拟旧方向历史已经被 130 次新观测淘汰，
以及解码器先输出后一帧的情况，验证每一帧仍使用自己的方向和接收时间。

### P2：没有对应方向元数据的原生输出仍可能未经转正就发布

此前在找不到输出 PTS 对应记录的分支中，只回填当前接收时刻，仍发布原始像素。
元数据淘汰、时间戳丢失或不匹配时，可能显示方向不正确的原生帧，与自动旋转约束冲突。

修复为发布前统一校验帧与元数据的时间戳、原生帧所需方向。无匹配记录、方向缺失
或记录属于别的帧时，拒绝发布并触发兼容回退；明确的 0 度方向仍被正确接受。
普通路径对未提供方向的帧维持既有兼容处理。

新增原生回归覆盖 PTS 乱序、超过方向历史保留时间的解码延迟、未知输出时间戳、
缺失方向、错误 PTS、0 度方向、元数据队列淘汰与解码器重置；原生协议测试通过。
本轮未修改型号目录、无线协商和 Python 辅助程序，也未新增实机旋转验收。
测试包已更新核心与哈希，上一轮 494 项 Python 及无线/应用回归结果仍适用于未改动部分。
